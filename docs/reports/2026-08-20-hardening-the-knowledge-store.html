Maintainability audit · media-tools + ~/.claude/knowledge

Hardening the Knowledge Store

The typed-claim system works and is measurably retrievable. Its weakness is not the data model — it is that every invariant is enforced by one machine's config, and the tools are wired into the repo by absolute paths carrying a username.

35 claims, 2 stores 115 retrieval assertions, 0 unfindable 10 findings 2 critical 2026-08-20

The closest thing to this in industry practice is the Architecture Decision Record (Michael Nygard, 2011; the MADR template). ADRs record a decision, its context and its status, and they are typically markdown in a repo. What this adds, and what ADRs conventionally lack, is three things worth naming: a type that makes a scopeless verdict unwritable, a collector that forbids two live answers to one question, and a retrieval test that fails at write time when a record cannot be found. Those are the parts that were bought with real mistakes.

Findings

F1Every invariant is enforced by one machine's configCritical

All four gates — type check, retrieval test, session injection, stagnation — live in ~/.claude/settings.json and ~/.claude/hooks/. None is in any repository. A clone on another machine, a git worktree used by a subagent, a reinstall, or a second person gets a project with all the discipline stripped out and no signal that it is missing. The rules survive only as prose inside the files they were supposed to govern.

Search handles: “works on my machine” · hermetic build · pre-commit framework (pre-commit.com) · CI as the source of truth · configuration as code — the enterprise rule is that a check a human can skip is a check that is not running.
F2The universal store has no remoteCritical

Nine cross-project laws, each one paid for with a measured failure, exist in exactly one place on one disk. media-tools is pushed to GitHub; ~/.claude/knowledge is a local git repo with no origin. This is the highest value-per-byte content in the whole system and it has the worst durability of anything in it.

Search handles: single point of failure · 3-2-1 backup rule · offsite replication · RPO (recovery point objective) — and note the store is small text, so the cost of fixing this is one private repo.
F3No schema version, so a field change breaks every existing storeHigh

Adding asked-as as a required field today invalidated all nineteen existing claims at once, and the repair was a throwaway script written in the moment. The next required field will do the same, and by then there will be stores in several projects, some not opened for months. There is no way for a tool to know which shape a file is written in.

Search handles: schema evolution · migrations (Flyway, Alembic) · expand–contract / parallel change · tolerant reader — stamp schema: N, ship a migration per bump, and let the checker upgrade in place.
F4The relevance test is circular and binaryHigh

Findability is asserted against asked-as — questions written by the same author, at the same moment, in the same frame of mind as the claim. That is the vocabulary problem measured against itself. It catches gross failure (it caught 44 of 44) and cannot catch the case that matters most: a question phrased six weeks later by someone who has forgotten the file exists. There are also no negative judgements — nothing asserts that a query must not return a particular claim — and the metric is binary recall@3, which cannot tell rank 1 from rank 3.

Search handles: qrels / relevance judgments · held-out evaluation · MRR and nDCG · negative judgments · query log mining — the durable fix is real queries from real sessions, not more authored ones.
F5No telemetry: dead claims and zero-result queries are invisibleHigh

Nothing records what was searched for or what came back. So there is no way to answer the two questions that actually drive maintenance: which claims has nobody ever retrieved (candidates for deletion or rewording) and which queries returned nothing useful (missing claims, or a wording gap). Without it the store can only grow, and growth without pruning is how the old markdown files failed.

Search handles: query log analysis · zero-result rate · dead code detection applied to docs · usage-driven deprecation — append one JSONL line per query; that is the whole implementation.
F6No freshness policy — nothing ever expires or gets re-reviewedMedium

Every claim carries verified-on and nothing reads it. The corpus is one week old so nothing is stale yet, which is exactly when the policy is cheap to install. A verdict about a tool's behaviour is a claim about a version of that tool; six months on it is a guess wearing a measurement's clothes.

Search handles: doc rot · TTL / review-by date · freshness SLO · CODEOWNERS · Google's “documentation freshness” practice — different kinds want different lifetimes: a law is timeless, a verdict about a dependency is not.
F7Referential integrity is partialMedium

Evidence paths all resolve today, but nothing checks them. One [[wiki-link]] already points at a memory file rather than a claim, and the route: field names tools in prose that nothing verifies exist. Each of these is a link that will rot silently the first time a file is renamed.

Search handles: referential integrity · link checker · foreign key constraint — check-routing.py already proves the pattern for one config; generalise it to every reference a claim makes.
F8No provenance: a verdict does not record the state it was measured inMedium

A claim says 16.28 versus 16.35 but not which commit produced those numbers. To reproduce or challenge a verdict you have to guess at the tree state from the date. One field — the SHA at verification — turns every claim into something a future session can check out and re-run.

Search handles: immutable audit trail · provenance · reproducible builds · ADR context section
F9A hand-rolled YAML parser that fails silentlyMedium

The frontmatter parser accepts a deliberately small subset and skips lines it does not recognise. That was the right call for a git-hook dependency, but silent skipping is the wrong failure mode: a claim written with valid YAML the parser does not implement loses a field with no error. Parse-don't-validate means unrecognised input is an error, not a shrug.

Search handles: parse, don't validate (Alexis King) · strict mode · fail fast · Postel's law considered harmful
F10Bookmarks accumulate with no triage pressureMedium

Four open items, none with a review date or an owner. Bookmarks were built precisely because deferrals get lost — but a bookmark list nobody prunes becomes the same backlog of good intentions in a new file format. Four is fine; forty is a graveyard, and nothing currently distinguishes the two.

Search handles: WIP limits · stale issue triage · backlog hygiene · bug bankruptcy

Plan

Tier 1 — do first

Make it survive leaving this machine

F1, F2. Nothing else matters if the system evaporates on a clone. Small, mechanical, high certainty.

  1. Vendor the tools into the repo and delete the absolute symlinks. media-tools/tools/ gets real files or a relative link into a checked-in knowledge-bin/; the username stops appearing in git objects.
  2. Add .claude/settings.json to each project with the four hooks, pointing at repo-relative paths. Project settings merge over user settings, so the machine keeps working and a clone inherits the gates.
  3. One entry point: make check runs type-check, retrieval, routing and the gate's own test suite. A human, a hook and CI all call the same target, so there is exactly one definition of “passing”.
  4. Push ~/.claude/knowledge to a private remote, and add a pre-push hook that runs make check.
  5. A GitHub Action running make check on push. This is the part that makes the invariants real rather than customary.

Tier 2 — next

Make the store defensible over months, not days

F3, F6, F7, F8. All cheap now, all expensive once several projects have stores.

  1. schema: 1 on every claim, plus knowledge-migrate.py that upgrades a store in place and refuses to read a version it does not know. Install it before the next required field, not after.
  2. Referential integrity in the type checker: evidence paths must exist, [[links]] must resolve to a claim, tools named in route: must be findable. Turn the one broken wiki-link into a failing test today.
  3. review-by derived per kind: a law never expires, a verdict about a dependency expires in 90 days, an open bookmark nags at 30. A --stale report, surfaced in the generated STATE.md.
  4. Stamp the verifying commit into every new claim automatically, so a verdict can be checked out and re-run.

Tier 3 — once there is usage to learn from

Let real queries drive relevance

F4, F5, F10. These need data the system has not produced yet, which is the honest reason to sequence them last rather than a reason to skip them.

  1. Log every query as one JSONL line — query, top three, scores, whether anything scored above a floor. This is the input for everything else here.
  2. Two reports from that log: zero-result queries (a missing claim, or a wording gap) and never-retrieved claims (delete, merge, or reword the asked-as).
  3. Upgrade the eval from binary recall@3 to MRR, and add negative judgements so “this query must NOT return X” is testable — the sibling-confusion failure that started all of this is exactly a negative-judgement bug.
  4. Triage pressure on bookmarks: an owner and a review date; the STATE.md report names anything past it.

What not to build

Pressure-testing the obvious upgrades

Not embeddings, not yet. The corpus is 35 claims. Dense retrieval earns its keep on vocabulary mismatch at scale; at this size the BM25 scores are already separated by a wide margin and asked-as covers the mismatch directly and legibly. Adding a model here buys a dependency, a cache and an opaque ranking, in exchange for a problem that is currently measured at zero failures. Revisit at a few hundred claims, or the first time the query log shows real zero-result queries.

Not a database. Files in git give diffs, review, blame, offline access and free history. A database gives none of those and would need all of them rebuilt.

Not a web UI. The consumers are a terminal and an agent. The SessionStart injection is already the interface, and it is pushed rather than pulled — which is the property that made it work.

The general shape of the argument: every one of those three is a real technique that solves a real problem, and none of the problems is currently measured as present. The discipline the store itself enforces — build the null before believing the number — applies to its own roadmap.
